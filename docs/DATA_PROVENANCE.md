# Data and artifact provenance

Baseline source: commit `203d5fe1ce71aac44e7ae7d55683aa45fd8591d0`. The original README describes these as simulated/dummy datasets. This is a source claim; no generator was found.

| File | Rows | Positive labels | Identifier |

| data/vessel_data.csv | 500 | 26 | vessel_id, unique per row |
| data/drone_data.csv | 1,000 | 81 | frame_id, unique per row |
| data/cyber_data.csv | 1,000 | 20 | log_id, unique per row |

No timestamps exist. The drone data contains categories and confidence values, not images. Cyber addresses use the private 192.168 prefix; the two IP octets used by the research model are constant.

The dashboard's two prediction CSVs each contain 200 rows. Their original split indices, row identifiers and probabilities are absent. The PNGs and model files are historical saved outputs, not outputs regenerated by this change.

`dashboard/artifacts.json` identifies the preserved source datasets and displayed assets by SHA-256. Hashes establish byte identity only. Training provenance, generation date, label authority and per-asset licensing remain unverified.

Before adding data, record its source URL/version, license and redistribution terms, acquisition date, intended uses, approval owner, schema, units, timestamps, retention, generation seed (if synthetic), label specification and transformations. Use synthetic or explicitly approved public data. Keep credentials and restricted data out of Git, screenshots, logs and demos.

Changing a manifest requires reviewing the associated data, chart/prediction consistency and tests. Do not update hashes automatically in CI merely to make integrity checks pass.
